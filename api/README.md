# API schema

`openapi.yaml` is the one description of the HTTP API. Java and TypeScript types are generated from it, and the build holds it to the server:

| Guard | What it checks |
|---|---|
| `ApiCoverageTest` | one operation per route in `docs/RBAC.md` (which `RbacMatrixTest` ties to the registered routes), with the same `x-bms-access`; every `$ref` resolves |
| `ApiSchemaTest` | boots the real app on SQLite and calls every operation, validating each JSON body, problem response and SSE payload against the schema; fails on drift or on an operation it never exercised |
| `RecordGeneratorTest` | the generated Java records on the class path match the current schema; every object schema is generated or listed with what serves it instead; no slice declares a record that duplicates a generated one (same components, order and types) unless it is allow-listed with a reason |
| CI, web job | `npm run gen:api` leaves `web/src/api/schema.d.ts` unchanged |

Response objects are closed (`additionalProperties: false`) with every field required, so a renamed, added or dropped field fails `ApiSchemaTest`. Change the schema in the same commit as the server.

## Java records

Every build generates one record per object schema into `target/generated-sources/openapi` (package `dev.thiru.bms.api.generated`), a main source root, and the slices serialise those records directly. There is nothing to run by hand: `mvn compile` regenerates them.

How the build does it (`pom.xml`):

1. `initialize`: a `maven-compiler-plugin` `testCompile` execution compiles the build-time source set `src/build/java` (`RecordGenerator`, `OpenApi`) into `target/codegen-classes`. `testCompile` is used because its class path carries the test-scope YAML reader; the reader is never a runtime dependency.
2. `generate-sources`: `exec-maven-plugin` runs `RecordGenerator` in process, on `target/codegen-classes` and its own `snakeyaml` plugin dependency, and `build-helper-maven-plugin` adds the output as a source root. Unchanged files are not rewritten, so an unchanged schema does not force a recompile; a record whose schema is gone is deleted.
3. `generate-test-sources`: `src/build/java` is also a test source root, for the schema tests.

The records are plain, with only `java.*` types: primitives for required fields of closed (response) schemas, boxed types in open (request) schemas so a missing field reads as null, string enums as `String`, `Instant`/`LocalDate`/`LocalTime` for times, `oneOf` skipped. Mainstream generators emit mutable beans with Jackson and Jakarta annotations, which is why this one is in-repo.

A slice maps its own values to the generated records (the `*Dtos` classes hold those functions). Generated records are a shared main package, like `kernel`, so using them does not couple slices. A slice must not declare its own copy of a schema shape: `RecordGeneratorTest` fails, unless the record is a use-case value allow-listed in `ALLOWED_DUPLICATES` with a reason.

## TypeScript types

`web/src/api/schema.d.ts` is generated by `openapi-typescript` (pinned at 7.4.4 in `web/package.json`) and committed:

```bash
cd web && NODE_OPTIONS=--max-old-space-size=512 npm run gen:api
```

CI runs `npm run gen:api && git diff --exit-code src/api/schema.d.ts`, so a schema change without regenerated types fails. Use the generated names instead of hand-written interfaces:

```ts
import type { components, paths } from "./schema";

export type Booking = components["schemas"]["Booking"];
export type SeatMap = components["schemas"]["SeatMap"];
type MoviesQuery = paths["/api/movies"]["get"]["parameters"]["query"];
type Problem = components["schemas"]["Problem"];
```

SSE payloads are `SeatMap` (`snapshot`), `SeatHeldEvent`, `SeatReleasedEvent`, `SeatBookedEvent` and `HeartbeatEvent`. `web/src/api/types.ts` is still hand-written; moving it onto these names is the UI's choice.
